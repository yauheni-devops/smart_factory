# Maintenance

Реестр оборудования, планы периодического технического обслуживания, наработка и заявки на работы. API работает на порту `8086`; экран `/ui` содержит сводку и отдельную вкладку «База и график ТО» с реестром оборудования и полным расписанием по регламентам. Для общих графиков и истории метрик используется Grafana + Prometheus.

Вход общий для главной страницы, мониторинга, выпуска, предупреждений и ПТО. При первом открытии главной браузер переходит на `/login?next=home`; после ввода логина и пароля возвращается на главную. Cookie действует 8 часов для одного имени хоста на разных портах, поэтому `localhost` и `127.0.0.1` нельзя смешивать при переходах. Кнопка «Выйти» завершает сеанс во всех разделах. Для запросов к API можно по-прежнему явно передавать HTTP Basic-заголовок. `/ui` и `/api/*` защищены, `/session` проверяет сеанс для frontend и telemetry, а `/health` и `/metrics` доступны для проверок и Prometheus. Логин и пароль задаются через `PTO_ACCESS_USERNAME` и `PTO_ACCESS_PASSWORD`; пароль должен содержать не менее 6 символов. Сеансы хранятся в памяти одного процесса и сбрасываются при его перезапуске; перед запуском нескольких экземпляров потребуется общее хранилище сеансов. Для публикации нужен HTTPS и длинный случайный пароль.

## Локальный запуск

Текущий локальный стенд использует SQLite в `data/maintenance.db`; этот файл исключён из Git. Compose применяет отдельную SQLite-копию в `data/local/compose/maintenance.db`, создаваемую скриптом `scripts/prepare_compose_data.py`, и открывает ПТО по адресу `http://localhost:8080/maintenance/ui`. Запуск описан в [`../../docs/container-runbook.md`](../../docs/container-runbook.md). Для нативного запуска задайте `DATABASE_URL` на `data/maintenance.db`, а `PTO_ACCESS_USERNAME` и `PTO_ACCESS_PASSWORD` — через переменные среды или корневой `.env`.

Первый контейнерный этап сохраняет SQLite. PostgreSQL, схема миграций и настройка резервного копирования запланированы после проверки этого локального Compose-сценария.

При первом старте сервис создаёт таблицы. После запуска `catalog` исходный список оборудования и интервалы импортируются запросом `POST /api/bootstrap/catalog` с авторизацией. Импорт идемпотентный; существующие записи ТО не перезаписываются. Даты последнего ТО не подставляются. Для долгосрочной эксплуатации автосоздание схемы следует заменить версионируемыми миграциями Alembic.

## API

- `GET /health` — проверка API и соединения с БД.
- `GET /api/dashboard` — сводка для интерфейса.
- `POST /api/bootstrap/catalog` — первичный импорт оборудования и графиков из каталога.
- `GET/POST /api/equipment` — реестр активов.
- `GET/POST /api/plans` — планы ТО и рассчитанный статус.
- `POST /api/meter-readings` — накопительные показания счётчика (уменьшение отклоняется).
- `GET/POST /api/work-orders` — список и создание заявок на работы.
- `POST /api/work-orders/{id}/complete` — закрыть работу, сохранить факт/простой и обновить базовую дату плана.

Состояния плана: `ok`, `due_soon`, `overdue`, `unknown`. Интервал «скоро» для dashboard по умолчанию — 30 дней или 100 моточасов. Регламент обслуживания вводится ответственным на основании паспорта/утверждённых требований.

## Grafana

Конфигурации Prometheus и дашборды Grafana находятся в `infra/observability`. В Compose они опрашивают внутренние API по DNS-именам. Для включения требуется задать `GRAFANA_ADMIN_PASSWORD` в локальном `.env` и запустить профиль `observability` по инструкции стенда. КТП видна по телеметрии, отдельный сервис `ktp` пока не реализован.

Метрики приложения и последние значения датчиков записываются в Prometheus. Для общей статистики узла (CPU/RAM/disk) позже потребуется Node Exporter; Grafana сама эти метрики не собирает.
